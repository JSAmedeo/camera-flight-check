# CLAUDE.md — Camera Flight Check Coding Agent Instructions

## Project Identity

**Camera Flight Check** (folder: `Camera Pre Flight Utility`) is a standalone Windows desktop utility that seasonal photo-set operators run before each shift at Cherry Hill Programs venues (Santa/Bunny sets). It walks the operator through a ~4-minute readiness check: getting-started splash (location + what you'll need) → set checklist → camera detection → grey-card calibration (auto-corrects the camera's white balance + exposure in-camera) → guided test-photo QA → hand off to RPS (the photo sales app).

The audience is non-technical seasonal staff, and per the user the reading/vocabulary level skews lower than typical software copy assumes — favor short, concrete, everyday words over abstractions or Latin-derived terms in every new string (e.g. "Skip this step," not "Not applicable"; "Skip and continue," not "Bypass" or "Override"). The UI is deliberately one-task-per-screen, plain English, big buttons. Preserve that tone in all UI copy — no jargon, no camera-speak beyond what the design already uses.

Two core UX principles established by the user, both worth checking any new feature against:
- **Never leave a detected problem unexplained** — if the app finds an issue it can't fix, it must say so and say why (see the "What we found / What we changed" cards).
- **Never let one unresolvable check trap the operator.** Some failures are outside their control (a hardware limit, a lighting problem that needs tech support) — any gate that can fail repeatedly for reasons the operator can't fix themselves needs an escape hatch after one retry, not infinite retries as the only path forward (see the Test Photo QA cards' "Skip and continue," and Set Checklist's per-card "Skip this step" for items a station genuinely doesn't have).

## Agent Autonomy and Permission Rules

**Bias strongly toward acting without asking.** The user has explicitly asked for fewer permission prompts. A broad tool allowlist lives in `.claude/settings.json` — keep it updated when a new command class becomes routine, rather than accumulating one-off approvals in `settings.local.json`.

Proceed without prompting for:
- Reading files, searching the codebase, inspecting assets
- Editing or creating source files (components, styles, helper code, config)
- Running `npm install` / `npm run *` / `npx electron*`, `dotnet build`, `python`, headless Chrome/Electron screenshot verification runs
- Building and packaging (`npm run dist`, `npm run package`)
- Launching the app and killing this project's own processes (`electron.exe`, `CameraHost.exe`, stray `python` servers) when needed to free the camera or iterate
- Probing the tethered camera with non-destructive helper commands (detect/settings/capture/release)
- Downloading well-known artifacts (npm registry, GitHub releases, SourceForge digiCamControl, Google Fonts) and extracting them in the scratchpad
- Creating folders, writing documentation, updating CLAUDE.md/CONTEXT.md/memory

Stop and confirm with the user before:
- Deleting files or directories that may contain user work (killing processes is fine; deleting their data is not)
- Architectural changes (switching desktop shell, replacing the camera stack)
- Changing settings **on the physical camera** beyond what the grey-card/QA flows themselves do
- Force-pushing or rewriting history on the remote (repo: https://github.com/JSAmedeo/camera-flight-check, private). Normal commits/pushes are fine; commit at meaningful checkpoints with descriptive messages. `main` holds field-validated states. `nikon-support` and `ui-revamp` were merged into `main` 2026-09-22 (field-tested end to end, including the grey-card escape hatch/flash-output fix) and are done. Day-to-day work now happens directly on `main`, one field-tested checkpoint at a time, unless something comes up big enough to need isolating on its own branch first (a call to make at the time, not a standing default)

## User Working Style

Same user as PhotoFlow Desktop. Processes progress visually — verify changes with real screenshots of the running app, not just green builds. Newer to many development stacks: give a short plain-language primer when introducing a new stack element. Work in small, verifiable stages with a visible running app. The user tests field builds on a real in-house station PC (1024×768 display, accessed over a PGI remote-desktop session whose down-scaling adds blur — remember that before chasing "blurry" reports).

Feedback consistently arrives as **annotated screenshots** — red circles, arrows, and handwritten notes marking up a real running-app screenshot rather than describing changes in prose alone. Treat the annotation's rough position as directional intent, not a pixel spec — the user has explicitly said their own hand-drawn placement can be "rough" and invited a better-phrased or better-laid-out result than literally what's circled. A single message routinely bundles **4-8 unrelated small changes** across different screens in one numbered list; work through all of them in one pass rather than asking which to prioritize, and call out any place a genuinely ambiguous item required a judgment call in the wrap-up rather than blocking on it mid-task.

## Actual Tech Stack (do not change without discussion)

- **Desktop shell:** Electron 31 — **interim scaffolding, not the destination.** The module may merge into PhotoFlow Desktop (Tauri v2). Do not deepen Electron-specific investment beyond what field validation needs. See CONTEXT.md § PhotoFlow convergence.
- **UI:** React 18 UMD + Babel standalone, loaded at runtime in `Camera Flight Check.html` — **no build step, no TypeScript, no bundler.** JSX files are plain `<script type="text/babel">` includes sharing global scope.
- **Styling:** plain CSS with custom properties. `simple-styles.css` is the design-synced base; all locally-added styles live in the `<style>` block of `Camera Flight Check.html`.
- **Strings:** ALL operator-facing copy lives in `strings.js` (`window.CFC_STRINGS`, loaded before the JSX) — training materials change, so **never hardcode UI text in JSX**; add a key to strings.js and reference `S.section.key` (templates use `{placeholders}` via the `fmt()` helper). Set Checklist tutorial images auto-load from `assets/tutorials/<key>-<n>.png` (see the README there) with a named placeholder until each file exists; each item's bullets double as its tutorial steps (title = bullet text) so guidance is authored once. Mall number→name lookup for the Welcome screen's location display comes from the fetched location directory (`help-feed.js`), which replaced the hand-maintained `assets/malls.csv` (retired 2026-09-23).
- **Camera layer:** `camera-host/` — .NET Framework 4.8 **x86** console exe wrapping digiCamControl's `CameraControl.Devices.dll` (Canon EDSDK 13.18.40 + Nikon PTP), plus raw EDSDK calls for card capacity. Speaks newline-delimited JSON over stdio (`detect`/`settings`/`capture`/`set`/`release`/`quit`). This and the grey-card math are the long-term keepers; keep them shell-agnostic.
- **Bridge:** `camera-bridge.js` (Electron main) spawns the helper or a built-in simulator; renderer reaches it via `window.cfc.camera` (see `preload.js`). Simulator supports env overrides for testing: `CFC_SIM_BATTERY=15`, `CFC_SIM_WB=Tungsten`.
- **Run log:** check-run events append to `%APPDATA%\Camera Flight Check\check-runs.jsonl` (`runs:save` IPC, `window.cfc.runs.save`), plus a per-run session file under `settings.paths.completionLogs` (one of three admin-configurable folders — see below). Records are API-shaped (`check_started`/`check_completed` with runId, locationNumber/locationName/station, ISO timestamps, duration; `screen_skipped` for Skip taps) — a future phase POSTs them to the company API, so keep the schema stable and additive. No operator name is collected (removed 2026-09-02 — Welcome no longer has a sign-in form). **`locationName` must be read from `settings.locationNameResolved`, not `settings.location.name`** — the latter is blank unless an admin typed an override, so reading it alone logged `null` at every station for a day after the mall CSV was retired (caught in the 2026-09-24 field logs, fixed same day). Anything else that wants the mall name has the same trap: the saved field is the *override*, the resolved one is the *answer*.
- **Settings surface (`main.js` `defaultSettings()`/`mergeSettings()`, admin-edited via the gear-icon Settings screen):** far more than camera limits now — `paths.{completionLogs,testPhotos,diagnostics}` (three separate configurable folders; only completionLogs and diagnostics are actually wired to a write target today, testPhotos is config-only, see Current Focus), `skipReasons` (admin-editable list, replaces the old hardcoded `S.skip.reasons`), `rpsLaunchEnabled`/`rpsPath`/`rpsAppName` (the exit-app default is now optional and nameable), `videoPlayerPath` (routes local video docs through a specific player instead of Windows' file-association chooser), `helpContacts`/`helpDocs` (admin-managed Need-Help content, reorderable), `helpAuto` (`feedUrl`/`seasonOverride`/`fetchRegional`/`fetchDistrict`/`placeholderRemoved` — the auto-filled Regional/District Manager contacts, see below), and `settingsPasswordEnabled`/`settingsPassword` (gates the whole Settings screen; ships **on** with default password `help123` — see gotcha #20 for how the lock UI is built). Nested objects need a matching entry in `mergeSettings()`'s deep-merge key list or a saved file predating that key loses it.
- **Vendored:** React/Babel/Geist font in `vendor/` (fully offline app — never reintroduce CDN links); digiCamControl 2.1.7 DLLs + VC++140 runtimes in `camera-host/lib/`.
- **App icon:** one source of truth, `assets/icon.ico` (16–256px, 32-bit alpha). Three consumers, all wired: `electron-packager --icon` in `scripts/dist.js` embeds it in the exe (which is what a desktop shortcut and the Start Menu read — a shortcut needs no icon file of its own), `setupIcon` in `scripts/package.js` gives Setup.exe the same one, and `BrowserWindow`'s `icon:` in `main.js` covers the taskbar and Alt+Tab while running. The top-bar mark uses `assets/app-mark.png`, the 256px image sliced byte-for-byte out of the .ico — sourced large deliberately, because the UI scales with real Chromium zoom (gotcha #13) and a 40px-native asset goes soft on bigger displays. **No `iconUrl`** is set on purpose: it only drives the Add-or-Remove-Programs entry and must resolve on the *target* machine, so a path into the build machine's `dist` folder would be missing everywhere else — that one entry shows a generic icon until the .ico is hosted at a real https URL.
- **Versioning:** bump `version` in `package.json` for each field drop (currently 1.5.1 — 1.5.0 was the location-directory/manager-contacts round 2026-09-23, 1.5.1 added the app icon and the Welcome copy split 2026-09-24) so installs and logs stay traceable. The exe's ProductVersion carries it too, so the running build can be confirmed from file properties without launching it.

- **Location directory (`help-feed.js`), 2026-09-23 (field-validated 2026-09-24):** the app's **only** outbound network call. Fetches the company location feed (a root-level array of ~552 mall records) once per launch in the background via `electron.net`. The feed is published **per season** and the URL is a template — `https://db0.cherryhillprograms.com:8090/atlaslist2?season={season}` — where `{season}` resolves to `S`/`B` + year (`S2026` = Santa 2026, `B2027` = Bunny/Easter 2027). `currentSeasonCode()` puts **Santa at Aug 1–Jan 31** (carrying the year of its own Christmas, so a January teardown still asks for the season that just ran) and **Bunny at Feb 1–Jul 31**; `helpAuto.seasonOverride` forces a specific code when a season runs long. Then it boils it down to ~145KB of `{mall, rm, dm}` keyed by normalized location number, and stores it as `location-directory.json`. **In a packaged build that file sits next to the exe** (the portable deploy folder) so it travels with the deploy, survives a profile rebuild, and can be **pre-seeded** by dropping a copy into the folder before handing a station over — which is how a site with no connectivity on setup day still gets its managers and mall name. `%APPDATA%\Camera Flight Check\` is the fallback when that folder isn't writable, and the only location in dev (where the "exe" is `electron.exe` inside `node_modules`). `locationDirectoryDirs()` in `main.js` defines the order; reads take the first hit, writes the first that succeeds. **Field-validated on a demo station 2026-09-24:** the station reached `db0.cherryhillprograms.com:8090` and fetched, a location number absent from the feed kept its saved name and showed no manager cards (the intended degrade), and **unpadded numbers typed by hand match** — `152` → Nittany Mall, `4` → Menlo Park — confirming `normalizeLocationKey` on both sides. Note ~17 real venues (mostly the 6-digit zoo/aquarium/attraction sites, plus Macy's Herald Square) genuinely carry `rm: null`/`dm: null` in the feed, so one card or none is correct there, not a bug. Note `npm run dist`/`npm run package` **wipe the packaged folder**, so a pre-seed copy has to be dropped in after packaging, not before. Everything the app reads comes from that file, which **never expires** — venues run on cellular routers that drop for hours, so a failed fetch is always a no-op and never a reason to show less. Feeds two things: the Welcome screen's mall name (the directory wins unless an admin typed a custom name — see `resolveLocationName`) and the auto-filled **Regional Manager**/**District Manager** contacts in Need Help. Those contacts are **derived per load, never stored in `helpContacts`**, are read-only in Settings, and can't be removed — only switched off — so a mid-season manager change reaches every station with nobody touching anything (IT is the admin and isn't on site). `settings:load` attaches `helpAutoRecord`/`locationNameResolved`/`helpAutoStatus`; **`settings:save` must strip all three** alongside `hostname`, and `settings:save` returns the full payload (not the bare persisted object) or the renderer blanks its mall name on every save. A successful refresh pushes `settings:changed` to the renderer (the only push channel in the app) so a station's first-ever fetch fills in mid-session; the push is held while Settings is open so an admin's draft can't overwrite it.
  - **Settings → General → Location & station** shows the live number and mall name beside their field headers, with both boxes locked (`.s-input--locked`) behind a "Change number" / "Change name" button. They're set once at install and then stamp every run that station logs, so a stray keystroke is the kind of thing nobody notices until runs arrive under the wrong venue. Editing the number re-resolves the name immediately through a dedicated **`location:lookup` IPC** — `settings.helpAutoRecord` is the record for the number already *saved*, so anything built on it stays a save behind while the admin types.
  - **The name box is never pre-filled with the looked-up name**, locked or not. Saving that would persist it and the station would permanently stop tracking a rename at source. Empty box = "use the location data"; text in it is an override, and the note underneath then shows what the feed actually says so the override is legible. Same reason the header shows the *effective* name while that note reads the *raw* record (`helpAutoRecord.mall`) — building the note on `locationNameResolved` echoed the admin's own words back at them as "From location data".

## Critical Gotchas (all hard-won — do not rediscover)

1. **`ELECTRON_RUN_AS_NODE`**: this IDE environment sets it, which makes `require("electron")` return a path string. Always launch via `env -u ELECTRON_RUN_AS_NODE npx electron .` (bash) — `npm run` scripts and `scripts/*.js` already strip it.
2. **camera-host must stay x86** — the vendored digiCamControl native DLLs (EDSDK) are 32-bit.
3. **`CameraControl.Devices` API drifts between versions.** Property types mix `PropertyValue<int>` and `PropertyValue<long>`. Before coding against the DLL, reflect over it with **32-bit** PowerShell (`C:\Windows\SysWOW64\...\powershell.exe`) — x64 processes can't load it. When a build "succeeds" suspiciously fast, check for errors hidden by `tail -1` and for a running `CameraHost.exe` locking `bin\Release` (taskkill it).
4. **DLLs must come from digiCamControl 2.1.7+** (SourceForge — the GitHub 2.0.0 release ships EDSDK 3.2/2016, which predates the Rebel T7 → "Not Supported" on `EdsOpenSession`). EDSDK 13.x natives need the VC++140 runtime DLLs vendored beside them.
5. **EDSDK needs a Windows message pump.** CameraHost runs `Application.Run()` on the main STA thread; camera calls marshal onto it via `OnPump()`; the stdio protocol runs on a background thread. Never block the pump thread waiting for a camera event (deadlock — see `Capture`).
6. **Settings load asynchronously after init.** `IsConnected=true` ≠ properties ready. `Settings()` polls until the ISO table is populated (the reliable signal, present even in Auto mode) — without this, a camera in M reads as all-nulls and the UI misdiagnoses "Auto mode." The UI separates `readFail` (nothing loaded → "Re-check / replug USB") from `modeWarn` (loaded but WB locked → genuinely Auto). Waiting also yields the body's real value tables (8 real ISOs) instead of the driver's static ones.
7. **The driver's value tables lie.** Static tables include phantom values (ISO 6/12 on a T7) and lens-impossible apertures. The correction planner clamps: **ISO 100–25600 only; aperture only ever stops DOWN** (brightening is ISO's job). Field-tuned tolerances live as constants in `simple-app-bundled.jsx`: `EV_TOLERANCE = 1.0` stop (user: under 1 stop is good enough), `CAST_TOLERANCE = 0.3` / `CAST_STRONG = 0.6` (|log2 R/B linear|), `CLIP_LIMIT = 0.2` (≥20% near-clipped pixels → color judgment unreliable, skip WB). Keep all of these in any new setting-writing code.
8. **Card-capacity reads use raw EDSDK and can block while the camera is busy** — `GetStorageInfoCached` reads once per session and never during `IsBusy`. Don't put EDSDK volume calls back in the `settings` hot path. Shots-remaining can be a garbage sentinel (T7: 1.9M) — UI ignores counts ≥ 100k.
9. **2.1.7 enumerates webcams** (incl. OBS Virtual Camera) as camera devices. `IsRealCamera`/`Priority` in `Program.cs` filter them — vendor-SDK devices outrank generic, webcams never eligible.
10. **Stale `CameraHost.exe` processes** survive force-closed sessions, hold the camera session, and block rebuilds — this bit the field machine as "failing to read camera settings" (2026-07-16). Hardened: the bridge taskkills orphans before every spawn, `main.js` holds a single-instance lock (skipped in `--screenshot` runs), and helper stderr persists to `%APPDATA%\Camera Flight Check\camera-host.log` (2MB rotation) for field debugging. Headless verification runs are a common orphan source.
11. **One app owns the camera USB session.** The check must `release()` before RPS opens (Done screen and `will-quit` both do). EOS Utility/webcam apps on the station PC can steal the session too.
12. **Cameras must be in M (or P/Av/Tv) mode** to accept setting changes; on Auto the camera reports WB/Tv/Av as null and refuses writes → UI shows the mode-dial warning.
13. **UI scaling is real Chromium zoom** (`setZoomFactor` from window size in `main.js`), NOT the CSS transform — the transform self-corrects to ~1. Never scale with CSS transforms (fractional bitmap scaling = blurry text). Mouse-coordinate math still divides by the residual scale (see `RegionSelect.rel()`). Launch size is adaptive: 85% of work area, 97% on displays under 900px tall.
14. **Post-`set` re-reads can time out** while the camera digests writes — `onRegion` tolerates a failed refresh and shows applied values instead of erroring. Show operators `errText(e)` (strips Electron IPC noise), never raw errors.
15. **Design origin:** UI sources come from Claude Design project `af76a28a-f036-4a45-b738-a5e2c2458ab3` — pull `.jsx`/`.css` sources, never the compiled `.html` bundles. `get_file` truncates at ~256KB, so the AI-photo assets can't be exported; local PNGs are SVG-rendered stand-ins.
16. **Headless verification pattern:** generate a `__verify.html` copy with an automation `<script>` (keydown/clicks/mouse events; remember the stage may not be mounted before ~3s), run with `--verify --simulate --screenshot=<path> --shot-delay=<ms>`, delete `__verify.html` after. Real-hardware runs need longer delays (EDSDK startup competes with Babel compile). These runs are a known source of orphaned `CameraHost.exe` processes (see #10). **Re-copy `__verify.html` after every source edit** — see gotcha #19, it's a snapshot, not a live view. When a CSS/layout fix visibly doesn't take effect and you're out of obvious guesses, don't keep guessing blind: inject a small script that reads `getBoundingClientRect()`/`getComputedStyle()` for the suspect elements and writes them into an on-page text banner (so they show up in the screenshot itself) — this found both the stale-copy issue and a shorthand/longhand CSS specificity bug (#21) in one session, in each case after guessing wrong once or twice first.
16a. **Field build version:** the packager deletes older-version portable zips, but always confirm which version the field machine is actually running before debugging "still broken" reports — a stale 1.0.0 folder once masked a day of fixes.
16b. **QA retake keep-levels:** `takePhoto(keep)` in `ScreenTestPhoto` — 0 resets all answers, 1 keeps "centered", 2 keeps "centered"+"crisp" (used via `pendingKeep` by the color-fix retake). Never pass the click event as `keep` (always wrap in an arrow). Colors always re-ask after a retake.
17. The **dev HUD** (compact pill top-right in the step-dots band) bypasses all step gates — kept intentionally during dev; removal/gating decision deferred. Don't put floating chrome at bottom-center; it collides with the app's footer buttons.
18. **`app.quit()` called a second time from inside a `will-quit` handler that already `preventDefault()`'d the first quit does NOT work** — Electron silently no-ops it: no error, no re-emitted `will-quit`, the process just hangs forever. This bit the async camera-release-on-close path (`will-quit` → `event.preventDefault()` → await `camera.releaseForHandoff()` → `app.quit()`), turning every app close into a multi-minute hang, confirmed via timestamped logging (`will-quit` fired once, the release resolved in 0ms, then nothing). Fix: call **`app.exit(0)`** instead of `app.quit()` once your own async cleanup is done — it bypasses the quit-event lifecycle entirely and actually terminates the process. Any future "do async work before quitting" hook must use this pattern, not a second `app.quit()`.
19. **`__verify.html` is a one-time snapshot copy, not a symlink.** The headless-verification pattern (#16) copies `Camera Flight Check.html` to `__verify.html` once, then re-runs Electron against that copy across several screenshot rounds. Any edit to `Camera Flight Check.html`'s CSS/JS made *after* the copy is invisible to `__verify.html` until it's re-copied — this produced two rounds of "why didn't my CSS fix work" in one session (a password-gate blur fix, then a needs-list padding fix), both traced by dumping `getComputedStyle()`/`getBoundingClientRect()` into an on-page debug banner rather than guessing. **Re-copy `__verify.html` from the source file after every edit you want reflected, not just once at the start of a verification round.**
20. **`backdrop-filter` on a full-viewport overlay blurs *everything* painted behind it, ignoring z-index tricks on specific elements you want to stay sharp.** A modal that needs part of itself to read clearly while a lock/gate sits on top of the rest (e.g. the Settings screen's "Application Settings" title staying crisp while a password prompt blurs the nav/body under it) can't solve this by bumping one element's `z-index` inside the blurred modal's own stacking context — that context is still painted as one atomic layer relative to anything outside it. The fix is structural: render the gate *inside* the same container, positioned to cover only the region that should blur (see `SettingsPasswordGate` + `.s-gate-inline`/`.s-settings-content-wrap`), not as a second full-viewport backdrop layered on top.
21. **Overriding one side of a shorthand property (`padding`, `margin`, etc.) with a same-specificity longhand rule doesn't fully win — the shorthand's other sides silently persist.** `.s-needs-box li { padding: 12px 0; }` and a later, equally-specific `.s-need-sublist li { padding-left: 14px; }` (one class + one element each) both apply: the longhand `padding-left` overrides cleanly, but `padding-top`/`padding-bottom` are still whatever the shorthand set, since they were never explicitly re-declared. This produced an invisible ~24px of unwanted vertical gap between Welcome-screen sub-bullets that looked like a flex/gap bug but wasn't. Fix: override with the **full shorthand** (`padding: 0 0 0 14px;`) or `!important`, not a single longhand property, whenever the conflicting rule you're overriding used shorthand.
22. **A time-filtered bulk delete on a directory the agent has been actively writing to can match and remove the directory itself, not just its newer children.** `find <dir> -newermt <ts> -exec rm -rf {} +` deleted an entire `calibrations` folder on 2026-09-20 — including real Canon T6 field-hardware diagnostic evidence from earlier that same session — because the directory's own mtime advances every time a child is created or removed, so it satisfied the time filter too, and `rm -rf` on a matched directory takes everything inside with it, old and new alike. **Rule: cleanup under any `settings.paths.*` directory (diagnostics/completionLogs/testPhotos), `%APPDATA%\Camera Flight Check`, or any other directory that may hold real field/user data must delete by exact, individually-named path captured right after creating it** (`rm -f screenshot.png`, `rm -rf calibrations/<exact-folder-name>`) — never a glob, `-mtime`/`-newermt` sweep, or wildcard against a shared directory. `pruneCalibrationDiagnostics()` in `main.js` is the reference-safe pattern (lists immediate children, deletes only specific ones past the retention cap by their own exact path, never touches the parent) — and as of this gotcha it doesn't even delete outright: pruned folders move to `calibrations\.trash\` and themselves age out on their own, longer retention (`CALIBRATION_TRASH_RETENTION`), so a bad prune or a repeat of this mistake has a recovery window instead of being unrecoverable.

23. **An oversized grid/flex item clamps to the start edge — it does NOT centre and split the overflow.** `place-items: center` on a 40px `.s-top-mark` holding a 48px image put all 8px of overflow *below*, sitting the top-bar mark 4px low against its title while the CSS looked correct (`.s-top-brand` was already `align-items: center`). Measured, not guessed: `mark mid 35.60 / img mid 39.61 / title mid 35.60`. The fix is to size the container to the item rather than overflow it — after that all three agree to 0.00px. Whenever a centred item is larger than its box, assume start-alignment and check `getBoundingClientRect()` midpoints rather than trusting `place-items`.
24. **A "locked"/read-only field style must differ from the base input's own background, or it's invisible.** `.s-input--locked` originally set `background: var(--card)` — which *is* `.s-input`'s background — so a locked box was indistinguishable from an ordinary empty one; only the text colour changed, and those boxes show placeholder text anyway. Confirmed by dumping computed styles: locked and normal both `rgb(37,44,59)`. What actually reads as locked is a *recessed* treatment — `--card-soft` (darker than the input default), a softer border and ~0.7 opacity → `rgb(32,38,52)/0.7` vs `rgb(37,44,59)/1`. Related: a locked box shouldn't echo a value that's already displayed elsewhere; it reads as a field someone failed to fill in. Show explanatory text instead and restore the real value on unlock so nothing has to be retyped from memory.

**Multi-venue field test, 2026-09-24 (logs committed under `field-test logs/`).** Three real venues — 1126 (Columbia Mall, **Nikon D3400**), 1181 (Boise Towne Square, Canon T7), 512 (Pueblo Mall, Canon T7) — plus a demo machine. Everything core worked at all three: the location feed reached each mall network and returned all 552 locations under `?season=S2026`, grey-card correction applied where needed (1126 ISO 400→100; 512 ISO 400→1600 + WB→Shade; 1181 no change), and every `camera-host.log` is free of error/fail/exception/timeout with a clean `exited 0`. Run durations were 87s / 30s / 47s — which is why the Welcome copy now says "about 2 minutes". Deployment itself is proven: an untouched machine taken through the Kaseya steps in DEPLOY.md launched with no SmartScreen or Defender prompt and needed no Defender exclusion. **Open items the logs surfaced:**
- **A station can carry exposure compensation the app ignores.** The D3400 at 1126 had **+2.7 EV** dialled in (the two Canons read 0.0). Its grey card came out 1.73 stops over; the app corrected by dropping ISO, but the compensation is still on the body, so the same overexposure returns next run and gets corrected again — the app fixes the symptom and can't fix the cause. It already *reads* `exposureComp` in the settings payload, so warning when it's non-zero is cheap and not yet done.
- **1181 sat 0.001 stops under the correction threshold** (`evDelta -0.999` against `EV_TOLERANCE = 1.0`) and reported "no change needed" on a frame essentially exactly one stop out. Not wrong, but that station is on the boundary and could flip either way run to run.
- A location number absent from the feed degrades correctly (keeps its saved name, shows no manager cards) — confirmed on the demo machine, which isn't in the mall list.

**Camera Setting Bypass (new screen), 2026-09-22:** a standalone "check or adjust the camera directly" screen reachable from a Welcome-screen button, for when an operator (or tech support) needs to poke at the camera without running the full pre-flight check. Connection status row with retry (`Check Connection`/`Try Again`) that correctly distinguishes not-yet-connected, connected, and lost-connection (mid-session disconnect) states; a Current Settings panel; a Manually Adjust Camera Settings panel (ISO/shutter/aperture/WB dropdowns + Apply); saved setting Presets (add/edit/reorder/remove/apply, matched to the nearest value the connected camera supports); and a live Take Photo test capture. Built and refined entirely via the headless-screenshot + debug-banner workflow (gotcha #16), then iterated across several rounds against real Canon hardware feedback:
- Current Settings and Manually Adjust Camera Settings frames are bottom-aligned via a `useLayoutEffect` that measures real `getBoundingClientRect()` geometry (top + natural bottom) rather than matching heights or guessing CSS padding — matching heights alone left them offset, since the two frames start at different Y positions. The effect's dependency array must include everything that can change what renders above either frame (connection state, errors, busy), not just the most obvious trigger.
- Take Photo's width is kept equal to the photo preview's own rendered width (narrower than its flex wrapper, since the preview is aspect-ratio-limited and centered) via a `ResizeObserver` that only writes to the button, never the observed element, avoiding any read/write feedback loop.
- A scrollbar that flickered on/off while Take Photo was held down was root-caused to the shared `.s-btn:active { transform: translateY(1px) }` press effect: the bottom-alignment fix above pins this column's content to fill its scrollable container with no slack, so the 1px press-transform alone was enough to tip it into overflow. Fixed by suppressing just the transform for this one button (`.s-bypass-photo-wrap .s-btn:active { transform: none; }`), not by touching the shared `:active` rule everything else in the app relies on.
- New `SI.cameraGear` icon (camera outline + gear badge overlapping the bottom-right corner, built from the existing `SI.camera` glyph and `SI.gear` path) replaces the plain gear on the Welcome-screen entry button, matching a reference image the user supplied.
- New simulator hooks in `camera-bridge.js` for reproducing hardware bug reports without a physical camera: `CFC_SIM_DISCONNECTED=1` (always reports disconnected) and `CFC_SIM_DISCONNECT_AFTER=N` (connects normally for the first N `detect()` calls, then reports disconnected — simulates a genuine mid-session drop).
